# cbv2g-grammar-sweep — reading all 4 792 generated grammars instead of the ones a corpus happens to touch

```bash
bash tools/cbv2g-grammar-sweep/run.sh                        # the commit the reports cite
CBV2G_SWEEP_REF=main bash tools/cbv2g-grammar-sweep/run.sh    # ...has anything moved?
```

The three filings in [`docs/reports/libcbv2g/`](../../docs/reports/libcbv2g/) were found by
round-tripping **our** ISO 15118-20 corpus through EXIficient. That bounds what can be found by what
our vectors exercise — and the filings themselves name the trap: *a generator that cannot emit a type
quietly removes it from everyone's coverage.* This looks at the generated code directly, so coverage
is every type in every schema family rather than every type we happen to send.

It needs Python 3 and, on a cold machine, network. Nothing in `dotnet test` touches it. Unlike
[`cbv2g-defect-probe/`](../cbv2g-defect-probe/README.md), which asserts the defects are still there and
is meant to stop passing, this one always exits 0 — it is a measurement. Read the counts.

## What it reads

cbexigen writes its model into the C it generates. Above each function, the content model it derived
from the schema:

```c
// Element: definition=complex; name={…}Body; type={…}BodyType; content type=ELEMENT-ONLY;
//          abstract=False; final=False; choice=True;
// Particle: AuthorizationReq, AuthorizationReqType (0, 1); AuthorizationRes, … (0, 1); …
```

and inside it, the state machine, one state at a time:

```c
case 179:
    // Grammar: ID=179; read/write bits=2; LOOP (VendorSpecificDataContainer), START (WPT_LF_DataPackageList), END Element
        // Event: LOOP (VendorSpecificDataContainer, …); next=180
        // Event: END Element; next=3
        done = 1;
```

Both halves parse, which turns the whole library into a labelled graph per type: 16 generated files,
976 functions with a grammar, **4 792 states**, 3 826 declared particles, 8 document grammars.

## The three checks

| | file | needs | what it decides |
|---|---|---|---|
| **1** | [`cbsweep.py`](cbsweep.py) | the checkout only | the state machines against themselves |
| **2** | [`cbdoc.py`](cbdoc.py) | the checkout only | the document element codes against EXI 1.0 §8.5.1 |
| **3** | [`cbschema.py`](cbschema.py) | + ISO's schemas | every type against the content model it was generated from |

**1 and 2 are reproducible by anyone**, which is the point of splitting them out: a filing that can only
be checked by someone holding an ISO licence is a filing that will not be checked.

**Check 1** — four invariants over the graph:

- *dead-end*: a reachable state from which no accepting state can be reached. The codec can never
  finish, so every schema-valid instance fails.
- *unreachable-particle*: a particle in the generator's own content model that no reachable state
  offers. The struct has the field and nothing can carry it. (Say *unreachable*, not *missing* — the
  state is usually generated and simply cannot be got to.)
- *event-codes*: each production's written code must be its index in the production list. Skipped
  where a state has a wildcard, whose code legitimately belongs to a second level.
- *code-width*: cbexigen's own rule is `ceil(log2(n+1))` over the listed productions.
- and *asymmetry*: the same state must carry the same grammar in the encoder and in the decoder.

**Check 3** enumerates the child sequences each content model permits — every optional taken and
skipped, every repeat at its minimum and one above, substitution groups expanded to their members,
attributes prepended — and walks each through the generated state machine. A sequence the schema
allows and the machine cannot walk is a document that cannot be encoded or decoded. It reports the
sequence, which is the form a maintainer can act on.

## What it does not decide

- **DIN 70121** is generated by cbexigen and its schema is not ours, so check 3 skips those 69 types.
  Checks 1 and 2 cover them.
- **Bit-level correctness.** Check 3 asks whether a document can be walked, not whether the octets are
  the ones a spec-built processor would write. That is what
  [`interop-exificient/`](../interop-exificient/) is for.
- **Anything about the runtime.** Buffer sizes, `ARRAY_SIZE` ceilings and the string-table limits are
  configuration, not grammar, and are left alone.

## Reading the output

Written to `$HOME/cbv2g-grammar-sweep/out` unless a directory is given. The counts as measured on
2026-08-11 against `03350be048b3` are in
[`docs/interop-runs/2026-08-11-libcbv2g-grammar-sweep/`](../../docs/interop-runs/2026-08-11-libcbv2g-grammar-sweep/notes.md),
which is also where the reasoning lives. Three of the five invariants in check 1 came back **clean
across all 4 792 states** — that is the more interesting half of the result and it is why the tool is
worth keeping rather than deleting after one use.
