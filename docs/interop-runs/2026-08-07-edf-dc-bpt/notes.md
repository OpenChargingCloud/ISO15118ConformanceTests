# 2026-08-07 — eVDriveFlow, DC_BPT: a bidirectional envelope, exchanged and read both ways

The last of the four capabilities eVDriveFlow was chosen for, and the one that needed a run rather than
a fix: their EV had been selecting **service 6 (DC_BPT)** out of our catalogue since the stdin wall
fell — but as a by-product nobody could see, because the verdict lived on a state machine that an
exception unwound past.

| | |
|---|---|
| Counterparty | [`EDF-Lab/eVDriveFlow`](https://github.com/EDF-Lab/eVDriveFlow) @ **`60249c3`**, their PKI regenerated by their own script |
| Ours | conformance suite @ `60eb3c8`, `EVSimulatorApp` @ `d7a5ee4` |
| Direction | `←SECC`, -20 DC, **Dynamic**, EIM, over **mutual TLS 1.3** (see [`2026-08-07-edf-mutual-tls13`](../2026-08-07-edf-mutual-tls13/notes.md)) |
| Deviation | `SOC=60` — one line in their `ev_dummy_controller`, inside the throwaway container, and the reason is below |
| Outcome | **Service 6 selected, and a real bidirectional envelope crossed in both directions**: their car 48 kW / 137 A of discharge, our station 50 kW / 200 A, each read by the other's decoder |

Artifacts: `bpt.flow.md`, `bpt.frames.log`, `bpt-envelope.txt`, `our-station.bpt.log`,
`their-ev.bpt.log`, `run-tls.sh`.

## What the run says about itself now

Our fixture used to print the selected service only after a clean session, and their EV has stopped
mid-charge-loop in every run so far — so the fact that it was choosing DC_BPT was visible only by
grepping *their* log. `InteropSession.RunSeccAsync` now hands the caller what the station learned even
when it leaves by throwing (`observed:`), and the fixture reports it from its `finally`, beside the
recording that was already there for the same reason:

```
TLS: Tls13, TLS_AES_256_GCM_SHA384, client certificate DC=VEHICLE, C=FR, O=EDF, CN=VEHICLECert.
Energy transfer service: 6 (DC_BPT) — their EV's pick out of our catalogue.
```

Our station offers `{2, 6}` (`Secc20Dc.EnergyServiceIds`) and their EV asks for **6** — the choice is
theirs, out of a catalogue that also contained the unidirectional entry.

## The envelope, both ways

The part that makes this a BPT result rather than a BPT-shaped one. `DC_ChargeParameterDiscovery`
carried `BPT_DC_CPDReqEnergyTransferMode` / `…ResEnergyTransferMode`, and each side's numbers were
decoded by the other's implementation — theirs OpenEXI/Nagasena, ours cbV2G-derived:

```
their EV -> us  (BPT_DC_CPDReq)          our station -> their EV (BPT_DC_CPDRes)
  EVMaximumDischargePower    48,000 W      EVSEMaximumDischargePower    50,000 W
  EVMinimumDischargePower       500 W      EVSEMinimumDischargePower         0 W
  EVMaximumDischargeCurrent     137 A      EVSEMaximumDischargeCurrent     200 A
  EVMinimumDischargeCurrent       1 A      EVSEMinimumDischargeCurrent       0 A
```

The car's envelope sits inside the station's, which is what the exchange is for. Their charge loop then
ran in `BPT_Dynamic_DC_CLReqControlMode` — the bidirectional *and* Dynamic variant — carrying
`EVTargetEnergyRequest` 53.6 kWh and `EVMaximumEnergyRequest` 67 kWh.

15 exchanges, every response code OK, ending where every eVDriveFlow run ends: their `hasattr` defect
in the charge-loop handler ([issue 2 of their report](../../reports/evdriveflow-headless-session.md)).
**No energy actually reverses**, then — the session dies before any discharge would be commanded. What
is proven is the negotiation: service, parameter sets, and both envelopes.

## The deviation, and why it was worth making

Run without it, their EV declares **zero** discharge capability:

```
EVMaximumDischargePower  0 (exponent -3, value 0)
EVMaximumDischargeCurrent 0
```

That is not a defect. Their `ev_dummy_controller` derives the discharge envelope from an
SOC-interpolated curve (`max_discharge_power = np.flip(max_charge_power)`, then
`np.interp(present_soc, …)`), and `present_soc` starts at **0** — an empty battery has nothing to give
back, which is physically right. The GUI's SOC field is what normally sets it (`ev_gui.py:686`), so the
headless path leaves the car flat: the same GUI/headless split that produced
[the `target_soc` finding](../2026-08-06-edf-stdin-wall/notes.md) the day before.

So `SOC=60` patches exactly one line — `self.present_soc = 0` → `60` — in their copy inside the
throwaway container, and the run records it as a deviation rather than hiding it. Both numbers are on
file: the zero-SOC run is the honest default behaviour, the SOC-60 run is what a car with something in
the battery declares.

## How to reproduce

Everything from the [TLS run](../2026-08-07-edf-mutual-tls13/notes.md), plus one environment variable:

```bash
SOC=60 bash run-tls.sh
```

The station side is unchanged — it always offered `{2, 6}` and always answered in kind.

## What this closes

All four capabilities this counterparty was picked for are now either done or explained:

| | |
|---|---|
| **-20 Ed. 1 at session level** | ✅ from the first run, 2026-08-01 |
| **Mutual TLS 1.3** | ✅ 2026-08-07, secp521r1 both ways |
| **Dynamic control mode** | ✅ 2026-08-06, end to end into the charge loop |
| **DC bidirectional** | ✅ this run — negotiated and parameterised in both directions |

What remains is not a capability but a defect of theirs: the charge loop past the first
`DC_ChargeLoopRes`. Fixed on their side, this same rig would run a bidirectional Dynamic session over
mutual TLS 1.3 to its end — which is as complete a -20 interop result as anything in this project.
