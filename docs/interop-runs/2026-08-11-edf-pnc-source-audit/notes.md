# 2026-08-11 — eVDriveFlow and Plug & Charge: **there is nothing to test against**

The `-20` Plug & Charge cell for this counterparty carried a `▢` and a condition:
*"first establish whether they do contract certificates at all; their documentation does not mention
them."* This is that. It is a source audit, not a session — the category
[`README.md`](../README.md) calls a **static sweep** — and it closes the cell by answering *no*.

| | |
|---|---|
| Counterparty | [eVDriveFlow](https://github.com/EDF-Lab/eVDriveFlow) **`60249c3`** (2023-04-17), and still `origin/main` on 2026-08-11 — **no upstream commit in two years and four months** |
| Method | read their tree; corroborate against wire bytes **already recorded** on 2026-08-01, so nothing was run and nothing of theirs was touched |

## The audit

**1. Neither role has a CertificateInstallation state.** `evcc/states/` holds 16 handlers and
`secc/states/` 17; the message appears in none of them. Their state machines run
`SessionSetup → AuthorizationSetup → Authorization → ServiceDiscovery → …` with no branch for it.

**2. The Plug & Charge vocabulary exists only where a code generator put it.**

| symbol | where it occurs |
|---|---|
| `ContractCertificateChain` · `PnC_AReqAuthorizationMode` · `SignedInstallationData` | `shared/xml_classes/…` (generated by xsdata), `shared/xsd_files/…` (ISO's schema), `doc/build/…` (Sphinx output of the bindings) |
| `OEMProvisioningCert` | the generated bindings and the schema, nothing else |
| `CertificateInstallationReq` | the same three, **plus** two timeout-table keys in `shared/global_values.py:51,57` |

Those last two are the closest thing to an implementation in the tree, and they are entries in the
Table 214 timing dictionaries — a number beside a message name, with no handler to time.

**3. Their own documentation does not claim it.** The README lists *Supported features*: DC
bidirectional power transfer with dynamic control mode, TLS 1.3 with mutual authentication, departure
time set from the SECC. Plug & Charge is not among them, and a case-insensitive search of `README.md`
and `doc/source` for `PnC`, `plug and charge` or `EIM` returns **nothing at all**.

**4. Both halves are configured EIM-only and behave that way.**

```python
evcc/ev_dummy_controller.py:111    self.authorization_services = [AuthorizationType.EIM]
secc/evse_dummy_controller.py:104  self.authorization_services = [AuthorizationType.EIM]
secc/evse_dummy_controller.py:105  self.certificate_installation_service = False
```

Their EV then raises on any advertised service outside that list — the defect already filed as
[`evdriveflow-authorization-setup.md`](../../reports/evdriveflow-authorization-setup.md).

## The wire agrees, and it cost nothing to ask

Their station's `AuthorizationSetupRes` was recorded on 2026-08-01 in the forward direction
([`…-edf-iso20-dc-notls`](../2026-08-01-edf-iso20-dc-notls/frames.log)); ours offering PnC was recorded
the same day in the reverse one
([`…-edf-iso20-dc-dynamic-reverse`](../2026-08-01-edf-iso20-dc-dynamic-reverse/frames.log)):

| whose `AuthorizationSetupRes` | on the wire | payload |
|---|---:|---:|
| **theirs**, shipped configuration | 28 B | **20 B** |
| **ours**, offering PnC and EIM | 46 B | **38 B** |

Eighteen bytes of difference, against a 16-byte `GenChallenge` plus a second entry in
`AuthorizationServices`. Their response has no room for a challenge and does not carry one. No new run
was needed to see it — the bytes were already in the repository, which is the argument for keeping frame
logs rather than verdicts.

## The latent defect, stated but deliberately not filed on its own

`secc/states/process_authorization_setup_request.py:28-31` fills the response from configuration and
then sets the authorization *mode* unconditionally, under its own marker:

```python
response.authorization_services = self.controller.data_model.authorization_services
response.certificate_installation_service = self.controller.data_model.certificate_installation_service
# TODO: given the services in authorization services, the response shall be eim or pnc
response.eim_asres_authorization_mode = ""
```

The service list is a **declared, typed field of their public data model** —
`EVSEDataModel.authorization_services: List[AuthorizationType]` at `secc/evse_controller.py:41`, and
`AuthorizationType` has a `PnC` member. The mode is not configurable at all.

So a station configured with PnC in that list answers `OK`, advertises PnC, and sends
`EIM_ASResAuthorizationMode`. Two requirements say it may not: **`[V2G20-1219]`** — if the SECC offers
"PnC" in `AuthorizationServices` it shall use `PnC_ASResAuthorizationMode`; and **`[V2G20-2568]`**,
which states the same duty independently. The mirror pair `[V2G20-1220]` / `[V2G20-2567]` is what their
line satisfies, and it is only correct while PnC is absent. The two elements are an `xs:choice`, so the
consequence is not cosmetic: with the EIM branch chosen there is **no `GenChallenge`**, an EV cannot
build `PnC_AReqAuthorizationMode` at all, and `[V2G20-2565]` — the SECC verifying the echoed challenge —
has nothing to verify.

**Why this is recorded here and not filed.** Three reasons, and the project's own rule for the third:

- They do not claim Plug & Charge. Filing *"your PnC path is wrong"* against a stack that never offered
  one is the kind of report [`reports/README.md`](../../reports/README.md) keeps out.
- It is **unreachable in the shipped configuration**. The default is `[EIM]`, and with that the handler
  is correct.
- Reaching it needs us to change their configuration, and the standing rule is that a finding
  *"is only reported if it survives without it"*. As a claim about their **source** it does survive —
  the line is unconditional in the published tree — so it is written down. As a claim about a running
  station it does not, because no such station exists unless we build one.

What it is worth is a sentence in the report that already covers the paired handler: their EV's crash on
a PnC-and-EIM offer is not only something a foreign station does to them. **Their own station will emit
exactly that offer if anyone sets the field, and without the challenge that would make it valid.** That
sentence is now in
[`evdriveflow-authorization-setup.md`](../../reports/evdriveflow-authorization-setup.md).

## What this does not decide

- **Nothing was run.** A station of theirs configured for PnC has never been on the wire, here or
  anywhere we can see. The byte comparison above is of their *shipped* configuration.
- **It is a claim about `60249c3`**, which is `origin/main` and two years and four months old. If the
  project wakes up, re-read before quoting — but the same check that dates it also ticks the *"has
  `main` moved?"* item that has been open on the filing since it was written.
- **`AuthorizationType` may carry more members than EIM and PnC.** The audit asked about contract
  certificates and answered that; it did not enumerate every authorization service in their enum.
