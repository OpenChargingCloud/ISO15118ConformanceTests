# The chain against eVDriveFlow — and the defect of ours it exposed, 2026-08-09

Third counterparty for the chain validator, and the first whose material is **secp521r1**. It was
meant to be a fourth confirmation. It is instead the run that found the validator's TLS call sites had
been throwing away half their input since the day they were written — and that a finding recorded
against EVerest the day before was ours, not theirs.

**Counterparty:** [`EDF-Lab/eVDriveFlow`](https://github.com/EDF-Lab/eVDriveFlow) @ `60249c3`,
unpatched, `SECURITY_PROTOCOL = 0x00` (their own switch), PKI regenerated by their own
`generateCertificates.sh`. **Ours:** `WWCP_ISO15118_SECC --listen 55000 --protocol 20 --mode dc
--dynamic --no-pnc --tls --server-cert <their SECC chain> --require-client-cert --trust-roots …`,
inside WSL, their EV in its container on an IPv6-capable docker network.

## Their hierarchy is shaped differently from everybody else's here

```
V2GRootCA  (DC=V2G, O=EDF) → cpoSubCA1     → cpoSubCA2     → SECCCert     (their station)
OEMRootCA  (DC=OEM, O=EDF) → VEHICLESubCA1 → VEHICLESubCA2 → VEHICLECert  (their car)
```

Two self-signed roots, and **the car's chain does not touch the V2G one**. That is what the CharIN V2G
PKI describes, and it is the first counterparty here to do it at TLS: Josev's own `CertPath` enum spells
its vehicle anchor `VEHICLE_ROOT_DER = "ca/v2g/V2G_ROOT_CA.der"`, so EVerest and Josev hang the vehicle
branch off the V2G root instead. Neither is wrong on the wire; a station's trust store has to be told
which, and that is the whole point of `--trust-roots` taking a directory.

## Three runs, one question each

Every run negotiated TLS 1.3 / `TLS_AES_256_GCM_SHA384`, mutual, **secp521r1 on both sides** — the
first P-521 chain this validator has ever judged.

| `--trust-roots` | Our station |
|---|---|
| their **OEM** root alone | `TLS client: chain valid, anchored at DC=OEM, C=FR, O=EDF, CN=OEMRootCA` |
| both VEHICLE Sub-CAs, **no** root | `chain REJECTED — unable to get local issuer certificate` |
| their **V2G** root — a real root, wrong branch | `chain REJECTED — unable to get local issuer certificate` |

`openssl verify` agrees on all three. Rows 2 and 3 refuse the handshake outright — the station answers
`The remote certificate was rejected by the provided RemoteCertificateValidationCallback` — while their
EV believes the handshake succeeded and sends its `SupportedAppProtocolReq` into a socket that is
already going away. That asymmetry is TLS 1.3, not a defect: the client finishes before the server has
ruled on the client certificate.

Row 1's session then ran its usual 62 messages to the charge loop and died in
`ev_dummy_controller.get_target_energy` on `None * int` — [issue 2 of their
report](../../reports/evdriveflow-headless-session.md), unchanged and unrelated. Chain validation
disturbs nothing.

## Row 1 could not have passed yesterday, and that is the finding

Their car sends `vehicleCertChain.pem` — leaf, `VEHICLESubCA2`, `VEHICLESubCA1` — so a root-only trust
store is enough. It was not enough, because **both .NET TLS call sites discarded the intermediates the
peer sent.** The validation callback's third argument is an `X509Chain` whose `ChainPolicy.ExtraStore`
holds exactly what arrived in the handshake; both sites wrote `(_, cert, _, _)` and validated the bare
leaf. A peer that sent a complete chain was judged as though it had sent nothing.

Measured rather than argued — the same peer, the same bundle, a binary built from the pre-fix source:

| | verdict on `CN=VEHICLECert` with their OEM root alone |
|---|---|
| before | `chain REJECTED — unable to get local issuer certificate` |
| after | `chain valid, anchored at CN=OEMRootCA` |

The BouncyCastle path never had this: it passes `c[0], c[1..]` — leaf and the rest of the peer's chain —
which is why the defect survived a day of use. Both paths now say the same thing.

## The correction this forces on yesterday's EVerest run

[`2026-08-08-everest-chain-validation`](../2026-08-08-everest-chain-validation/notes.md) recorded, as
its first row, that their V2G root alone could not build a chain, and explained it: *"EVerest's station
sends only its leaf — no CPO Sub-CAs on the wire."* **That explanation is wrong.** Asked directly, with
no code of ours in the way:

```
$ openssl s_client -connect … -showcerts
 0 s:CN=SECCCert,   O=EVerest, C=DE, DC=CPO   i:CN=CPOSubCA2, …
 1 s:CN=CPOSubCA2,  O=EVerest, C=DE, DC=V2G   i:CN=CPOSubCA1, …
 2 s:CN=CPOSubCA1,  O=EVerest, C=DE, DC=V2G   i:CN=V2GRootCA, …
```

Three certificates. Their station sends its full chain. Re-run today against the same station with the
fix in place:

| `--trust-roots` | Our EVCC, today |
|---|---|
| their V2G root **alone** | `chain valid, anchored at CN=V2GRootCA` — yesterday: rejected |
| root + both CPO Sub-CAs | `chain valid, anchored at CN=V2GRootCA` |
| both CPO Sub-CAs, no root | `chain REJECTED` — unchanged, and still the right answer |

So of yesterday's three rows, **the first was our defect**, the second was right for the wrong reason
(the bundle worked because it carried the intermediates our code refused to read off the wire), and the
third stands untouched: a non-self-signed certificate in the trust store is never an anchor. The
reason text on that third row has changed — `unable to get local issuer certificate` rather than
`terminated in a root certificate which is not trusted` — because the peer's own Sub-CAs now build the
path as far as `CPOSubCA1` before it runs out of root, which is a more accurate description of the same
refusal.

**Worth naming, because it is the part that generalises.** The wrong conclusion survived because it
*agreed with something this repository already believed* — a note about `Evse15118D20` sending a bare
leaf, carried over to `EvseV2G` without being re-measured. A negative result that confirms an
expectation is the one nobody checks. What broke it was not more care with the same counterparty; it
was a different counterparty whose chain has a different shape.

## What changed, and what is now tested

- `TrustRoots.PeerIntermediates(X509Chain?)` — new, and the piece whose absence was the bug.
- Both call sites in `WWCP_ISO15118_SECC/Program.cs` and `WWCP_ISO15118_EVCC/Program.cs` now pass it.
- `Security/ChainValidationTests.cs` — five tests, the validator's first coverage of any kind. The
  load-bearing one is `RootOnlyTrust_NeedsThePeersIntermediates`: root-only trust validates a leaf **if
  and only if** the peer's intermediates are handed over.

## Still out of reach here

`--tls-backend bc` at the **station** cannot be pointed at a foreign PKI: `SeccPki.Generate` mints its
own hierarchy and pins the expected vehicle leaf, so there is no way to serve eVDriveFlow's SECC chain
over it or to accept their car. The BouncyCastle chain path is therefore still judged only by material
we minted — on the EVCC side `--vehicle-cert` does load real credentials, so the forward direction
could close it. Not attempted today.

## Rig notes

**The docker network must be created with IPv6**, and re-created after a WSL restart:

```bash
docker network create --ipv6 --subnet fd00:edf::/64 --subnet 172.30.0.0/16 edfnet
```

Their EV discovers a station by SDP multicast to `ff02::1`; on an IPv4-only network it logs
`[Errno 101] Network is unreachable` once per attempt and never connects. Recreating the network
without `--ipv6` cost the first run of the day — the switch is in the
[2026-08-06 note](../2026-08-06-edf-stdin-wall/notes.md) and not in the run scripts, which is why it
was easy to lose.

Their PKI regenerated on 2026-08-07 is still valid: `seccCert` runs to 2026-10-05, the 60-day SECC leaf
ISO 15118 asks for. `secc.pfx` is not kept between runs and is rebuilt from their `seccCertChain.pem`.
