## Finding 1 — their TLS profile contains neither cipher suite ISO 15118-2 prescribes

Both of their shipped configs — EVCC *and* EVSE — pin the GnuTLS priority string

```
SECURE128:-VERS-SSL3.0:-VERS-TLS1.0:-ARCFOUR-128:+PSK:+DHE-PSK
```

Expanded (`their-cipher-suites.txt`), its ECDSA half is AES-GCM, AES-CCM, ChaCha20-Poly1305, and two
SHA-1 CBC suites. **`TLS_ECDHE_ECDSA_WITH_AES_128_CBC_SHA256` (0xC0,0x23) and
`TLS_ECDH_ECDSA_WITH_AES_128_CBC_SHA256` (0xC0,0x25) are absent** — and those two are exactly what
ISO 15118-2 requires of a -2 TLS session, and exactly what our station pins
(`TlsProfiles.Iso2CipherSuites`).

The result is not subtle:

```
System.Security.Authentication.AuthenticationException
  ---> Interop+Crypto+OpenSslCryptographicException : error:0A0000C1:SSL routines::no shared cipher
```

A station that implements the standard's TLS profile and a car that uses their configuration **cannot
complete a handshake at all.** Their own pair interoperates because both ends share the same
non-conformant profile.

This is less a slip than an era gap worth naming: GnuTLS's curated `SECURE128` list has dropped the
SHA-256 CBC suites as legacy, so *any* stack that reaches for a modern curated list loses precisely
the suites a 2014 standard made mandatory. Which is the more defensible position is not this
project's call — but a run that only reported "TLS works" would have hidden the question entirely.

## What made the rest of the run possible, stated as a deviation

`V2G_INTEROP_TLS_SUITES=platform` unpins our suite list for the run, so the two sides can find the
intersection their profiles do have. The environment variable exists *because of* this run and says so
in its own documentation: it is the one case the pinning warning in `TlsOptions.CipherSuites` does not
cover — a peer offering none of the profile's suites. With it, the conformance claim about suites is
simply not made, and everything above TLS becomes testable.

Negotiated, read back from the live `SslStream` rather than assumed:

```
TLS: Tls12, TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384, client certificate none.
```

TLS **1.2** is still pinned, and correctly so — that half of the -2 profile they do satisfy.

## What ran

SDP first, and it carried the news: our advertisement announced TLS, and their EVCC branched on it
before opening the socket — `v2g-sdp-async: tcp[tls]://[fe80::…]:55000`. Then:

```
0  SupportedAppProtocolReq     → SupportedAppProtocolRes     OK_SuccessfulNegotiation
1  SessionSetupReq             → SessionSetupRes             OK_NewSessionEstablished
2  ServiceDiscoveryReq         → ServiceDiscoveryRes         OK
3  PaymentServiceSelectionReq  → PaymentServiceSelectionRes  OK
```

Four exchanges over TLS, every code OK — and then their injector stopped.

## Finding 2 — their EVCC signs the AuthorizationReq whenever TLS is configured, not when the session is Plug & Charge

```
--[pkg:68] SimulationStatus::Fail  iso2:authorization_req
           error: {"uid":"iso2-pki-sign-sign","info":"error:no_challenge"}
```

The scenario is the captured Audi's, and it selects `"option":"external"` — **EIM**. No
`PaymentDetailsReq`, therefore no `GenChallenge`, therefore nothing a signature can echo. Their EVCC
tried to sign anyway.

In their source the decision is one `if`:

```rust
// exi-15118/src/net-exi.rs:187
if let Some(pki) = self.pki_conf {
    match tag_id {
        … | MessageTagId::AuthorizationReq | MessageTagId::MeteringReceiptReq =>
            exi_doc.pki_sign_sign(tag_id, &pki.get_private_key()?)?,
```

The condition is *"a `pki` block is configured"*, not *"this session selected Contract"*. Their TLS
config always carries one — `binding-start-evcc --pki_tls_sim_dir` is how their README tells you to
enable TLS — so over TLS every `AuthorizationReq` is signed, EIM sessions included.

**Confirmed against their own responder.** Their injector and their EVSE binding, both TLS, both their
PKI, their shipped scenario, their documented command line — same failure, same transaction:
`their-pair.injector.log`. So the shipped Audi scenario cannot run over TLS *at all*, against any
station including their own, and our station is not implicated. That also means their README's TLS
quick-start — the `audi-dc-iso2-compact.json` line with `--pki_tls_sim_dir` — cannot succeed as
written.

## Finding 3 (positive) — mutual TLS works, at -2

Their EVCC config carries a client chain, so a second run required one
(`V2G_INTEROP_TLS_REQUIRE_CLIENT=1`, accept-any):

```
TLS: Tls12, TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384,
     client certificate DC=end, CN=eMaid, OU=redpesk security, O=IoT.bzh, S=Breizh, C=FR.
```

Their car presents its certificate on demand and the session runs exactly as far as before. Mutual TLS
at ISO 15118-2 is unusual — the standard requires it only at -20 — and this is the first time a
counterparty's car has presented one to our station in a **-2** session.

## What this needed on our side

The reverse fixtures could not serve TLS at all: all four built a plaintext `TcpV2GListener`, and the
Josev `←SECC` TLS cell in the matrix was driven by the CLI, which does not record. So
`InteropEnvironment.ServerTlsOrNull` is new — `V2G_INTEROP_TLS_SERVER=<pfx>[:password]`, with
`V2G_INTEROP_TLS_REQUIRE_CLIENT=1` beside it — and the tux fixture now derives three things from that
one value: the listener's TLS, what SDP advertises, and the recording's name. A station advertising
TLS while listening in plaintext is discovered and then fails its handshake, which reads as a peer
defect; deriving them from one value makes that impossible to get wrong.

Unlike the client side there is no permissive dev shortcut here, and that is the point: in reverse
*we* are the one being trusted, so the only material that can work is the counterparty's own.

## How to reproduce

```bash
# their PKI, with their own script (needs gnutls-bin for certtool)
sudo cp iso15118-simulator-rs/afb-test/certs/templ-*.cfg /usr/share/iso15118-simulator-rs/
bash iso15118-simulator-rs/afb-test/certs/mkcerts.sh -i ~/tux-evse/run/pki

# the certificate our station presents is theirs: _server.pem + its key, as a PKCS#12
cd ~/tux-evse/run/pki && openssl pkcs12 -export -inkey _server_key.pem -in _server.pem \
    -certfile _root.pem -name tux-evse-server -passout pass:interop -out server.pfx

# ours (namespace + relaxed scenario as in the plain-TCP run)
V2G_INTEROP_LISTEN=55000 V2G_INTEROP_SDP=evse-veth V2G_INTEROP_PROTOCOL=2 V2G_INTEROP_MODE=dc \
V2G_INTEROP_TLS_SERVER=$HOME/tux-evse/run/pki/server.pfx:interop \
V2G_INTEROP_TLS_SUITES=platform \
V2G_INTEROP_RECORD=/tmp/tux-tls V2G_INTEROP_SCENARIO=$PWD/audi-relaxed.json \
  dotnet test -c Release ISO15118ConformanceTests.Simulation \
    --filter "FullyQualifiedName~TuxEvseInteropTests.TheirInjector"

# theirs, in the namespace: same as the plain run but with the TLS config and PKI_TLS_DIR
sudo ip netns exec tuxev env PKI_TLS_DIR=$HOME/tux-evse/run/pki … \
  afb-binder --name afb-evcc --config=…/binding-simu15118-evcc.yaml --config=audi-relaxed.json
```

Drop `V2G_INTEROP_TLS_SUITES=platform` to reproduce finding 1, and add
`V2G_INTEROP_TLS_REQUIRE_CLIENT=1` for finding 3.
