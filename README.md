# Vanaheimr.V2G.Exi.Prototype

Prototype EXI codec for ISO 15118 AppProtocol messages, .NET 10, AOT-friendly.
Wire conformance is anchored by a vector suite whose `expectedHex` is generated by
EVerest's libcbv2g (pinned commit) — see `tools/cbv2g-ref/`.

## Run

```

```

## What "green" means today

The vectors in `Vectors/AppProtocol.vectors.json` carry `expectedHex` produced by
**EVerest's libcbv2g** (pinned commit `03350be`), the de-facto ISO 15118 reference
codec. A green run therefore proves **wire conformance**, not just self-consistency:

- Our encoder produces byte-for-byte the same EXI stream as cbV2G.
- Our decoder reads cbV2G's bytes back to the original message.
- The source-generated codec matches the hand-written one byte-for-byte (and thus
  cbV2G too — the `GeneratedCodecDiffTests` couple them).
- Every vector also round-trips through cbV2G itself (verified by the regeneration
  driver's `encode → decode` check).

The reference oracle and regeneration workflow live in
[`tools/cbv2g-ref/`](tools/cbv2g-ref/README.md); pin bumps update both the CMake tag
and the vector file's `referenceEncoder.commit`.

### The wire model (learned from cbV2G)

ISO 15118 / cbexigen use a **non-strict** schema-informed EXI grammar: every
structural transition carries an explicit event code (2-bit document selector; per
simple field an SE bit, a value-start bit and an EE bit; 2-bit list-loop / optional
codes). The earlier prototype assumed an over-optimised *strict* grammar with 0-bit
event codes — internally consistent, but wire-incompatible. Both the hand-written
codec and the source generator were corrected to the non-strict model.

## Failure output

When `expected != actual` the test names the vector, prints both byte
sequences, and pinpoints the first differing byte plus the bit-position within
that byte (MSB-first, matching the EXI bit-packed convention). This is the
output you want when staring at the third byte of `0xFE` wondering whether the
Priority field shifted by one.

## What this prototype still does NOT do

- EXI string value tables (only "miss" — fine for AppProtocol, blocker for -2/-20).
- Non-ASCII string values (cbV2G rejects code points > U+007F; our codec would
  encode them rune-wise, but that path has no reference oracle yet).
- Lenient decoder mode for interop debugging.
- Header options document (AppProtocol doesn't use it; ISO 15118-20 may).
- The real schema surface (imports, choice, substitution groups, attributes,
  XMLDSig) — the generator still only handles the small AppProtocol XSD subset.

## Next milestones

Phase 0 (wire conformance for SupportedAppProtocol) is **done**: the vectors come
from cbV2G, and both codecs match it. See `docs/roadmap.md` and `docs/prompts/` for
the full plan. Immediate next steps:

1. String value tables (local + global partitions) — mandatory for -2/-20.
2. Remaining EXI datatypes (signed integer, binary, boolean) + W3C EXI testsuite.
3. Grow the source generator to the real ISO 15118-2 schema set (Phase 2).
4. ISO 15118-2 messages + XMLDSig (Phase 3), then ISO 15118-20 (Phase 4).
